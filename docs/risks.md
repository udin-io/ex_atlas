# Risks

This page lists the risks found in ExAtlas's code comments, guides and
`CLAUDE.md`, each with what we watch and what we would do. PR #70 creates it.
It feeds the choice of the next ticket: a risk with no mitigation is a
candidate. Kinds: technical (T), operational (O), product (P).

| # | Kind | Risk | What we watch | What we would do |
|---|---|---|---|---|
| 1 | T | RunPod does not document how far its billing API lags. `compute_spend/2` is not a live cost, so a low bill may only be late | `{:spend_reconciled, ...}` events: `billed_usd` far below `estimated_usd` after hours | The estimate fires the cap; the bill only raises spend. Measure the lag against a live pod, then document it |
| 2 | O | CI is red at `hex.audit` on cowlib 2.20.0 (EEF-CVE-2026-43966, EEF-CVE-2026-43969), no fixed release. Cowlib comes in only through test-only `bypass`. Sobelow and `mix test` never run on Actions | A cowlib release past 2.20.0 | Upgrade, then the step passes. Until then run the steps after `hex.audit` by hand and report the test count. Never add an ignore (decision 4 on #53) |
| 3 | O | The default DETS tracking store lives on the machine's own filesystem. On Fly without a volume it comes up empty every deploy; adoption does nothing and the Reaper deletes the pods. `TrackingStore.Ecto` (#120) removes it for a host that uses it; the default and the guides still point at DETS until slice 2 | Hosts using `persist: true` with the DETS default and no `:storage_path` on a mounted volume | Use `TrackingStore.Ecto` with `ExAtlas.Orchestrator.Supervisor` after the repo, or mount a volume. Slice 2 makes the installer write the Ecto setup |
| 4 | O | The Reaper reaps nothing for the whole boot when the store cannot be read (`:adoption_failed`), or when the node has no `reap_owner` and sees peers, or when another node reports the same owner | Error logs from `Reaper` | Fix the store or set a unique `reap_owner`. A leak is bounded by `max_runtime_ms` |
| 5 | O | A node with no owner and no peers reaps every untracked pod with the prefix, including pods of machines that share the account without clustering | Deployments with several machines on one account | Set `reap_owner` per machine |
| 6 | O | Pods of a node that is gone, pods named before the owner was set, and other nodes' pods are only logged once per boot | Reaper logs | The operator deletes them by hand |
| 7 | T | A RunPod pod keeps running and billing after its container exits. Only self-termination or `max_runtime_ms` ends it. A Lambda instance cannot delete itself: only the host's finish report, which the tracker turns into a terminate, or `max_runtime_ms` ends it | Task sessions that outlive their command | `run_task/1` defaults both on; keep `self_terminate` unless you accept the backstop only. On Lambda, `command:` with `self_terminate: true` and no `callback:` is `:validation` (#85) |
| 8 | T | Without a finish report, `{:task, :completed}` means the container ended, not that it succeeded | Tasks that report no exit code | Use `ExAtlas.Callback` so the exit code is proven |
| 9 | T | Preemption is inferred, not reported: a `spot: true` pod that disappears is called `:preempted` | Respawn loops | Accept it; RunPod no longer sells spot pods and `spot: true` returns `:unsupported` there |
| 10 | T | Cost estimate leaves seconds uncounted: the provider call before the tracker starts, and the overlap between a replacement's spawn and the old pod's DELETE | Spend against bill | Seconds against a cap in dollars; accepted in #28 |
| 11 | T | An `EXITED` RunPod pod reads `cost: 0.0` while its disk still bills | Exited pods the tracker did not delete | `UpstreamStatus` ends the session on `EXITED`, so the estimate stops with it; the disk bill is outside the cap |
| 12 | T | Rolling back to a build before #69 leaves records written since the upgrade unadopted (older builds skip version 3 records) | Rollbacks while `persist: true` tasks run | `stop_tracked/1` those tasks first, or delete pods and records by hand |
| 13 | T | A host store that maps record fields to columns needs the four cost columns, or an adopted task's budget starts fresh | Host `TrackingStore` implementations | Add `:max_cost`, `:spent_usd`, `:cost_rate`, `:cost_since_ms` |
| 14 | O | Live RunPod tests (`--only runpod_live`) spend real money and are excluded from `mix test` and CI | Nobody runs them | Owner runs them with their own key |
| 15 | T | With Hex 2.5, local `bin/ci` also stops at `hex.audit` on cowlib, so it never reaches sobelow or `mix test` | A `bin/ci` run that ends at `hex.audit` | Run the later steps by hand and report each count and exit code |
| 16 | T | After a respawn and then a node restart, the bill for the current pod is compared with the whole session's stored spend, since the record does not say which pod spent it. A bill can then raise the spend by less than it should (cap $10: $4 on pod A, $1 estimated on pod B billed $5.50 raises spend to $5.50, not $9.50) | Respawned tasks that are adopted with `persist: true` and `max_cost` | Store the current pod's starting spend in a version 4 record, with a new column in host stores |
| 17 | T | `s3:` credentials sit in a third-party GPU pod's environment, readable by anyone with access to that pod | Callers passing long-lived, bucket-wide keys | Scope keys to the two prefixes with a session token, or pass presigned URLs (#73), which reach one object each until they expire |
| 18 | T | We assume RunPod's `POST /v2/pods` response echoes `env` as `GET` does. `Spec.Compute` hides `raw` from `inspect/1` either way, but `compute.raw["env"]` holds the credentials for code that reads it | Code that logs `compute.raw` | Read `raw` only for fields ExAtlas does not normalize; never log it |
| 19 | T | Whether RunPod v2 merges a body's `env` into a template's or replaces it is unknown; with `template_id`, the staging variables may replace the template's env | Pods spawned with `template_id` and `s3:` | A live probe with a template that sets env |
| 20 | T | `guides/scripts/atlas_entrypoint.sh` is tested against a stub `aws`, never a real store. Command lines follow aws-cli's documented syntax; behaviour against Tigris, R2, MinIO and S3 is unverified | Reports of failed pulls or uploads on a real store | Run the script once against each store and record the result here |
| 21 | T | The script's log copy waits for every process that holds the trainer's stdout open, so a trainer that leaves a background process delays the upload until it exits | Tasks whose upload comes late | Redirect background processes' output away from stdout, or ask for a bounded wait |
| 22 | T | Once `RunPod.Client` reveals a credential, Req holds it. Req's `inspect/1` shows the first 3 characters of the `authorization` header and of `:auth`, and a custom header from `req_options: [headers: ...]` in full | Crash reports from inside Req's steps | Pass credentials through `api_key:` or `req_options: [auth: ...]`, not a custom header |
| 23 | T | The caller's own frames hold what the caller passed. A crash in the caller's code, or in `ExAtlas.await_ready/2`'s loop, prints a plain-string `api_key:` | Crash reports from host code | Pass `api_key: ExAtlas.Secret.wrap(key)` |
| 24 | T | `ExAtlas.Secret` holds its value in a closure, which raises `BadFunctionError` once `ExAtlas.Secret`'s code is purged twice. A hot code upgrade that reloads it twice breaks every running tracker's provider calls | Hosts that hot-upgrade ExAtlas | Restart trackers after the upgrade; releases that restart the node are not affected |
| 25 | T | Only `api_key:`, the `:auth`, `:headers`, `:aws_sigv4` entries of `req_options:` and the `env:` values are sealed. A key in `base_url:` user info or in `req_options: [params: ...]` prints as given | Hosts that put credentials anywhere else | Pass them through `api_key:` or `req_options: [auth: ...]` |
| 26 | T | RunPod's spawn request carries the pod's bearer token, the callback token and the `s3:` secret in its JSON `env`, and Req's `inspect/1` prints `json` in full. A crash in a frame holding that request would print them (not observed) | Crash reports from inside Req during a spawn | Build the body as late as possible; ask Req upstream to redact `json` |
| 27 | T | A `Secret`'s closure carries its value in `term_to_binary`, so an `erl_crash.dump` or a message sent to another node holds it. No ExAtlas event or record carries a Secret | New events or records that include opts | Keep opts out of events and records; scrub before `term_to_binary` |
| 28 | P | A `persist: true` task with `s3:` that is preempted after a restart, and has no `respawn_credentials:` resolver (per task or in app config), ends with `{:respawn_failed, ...}`: the record holds no credentials. #87 added the resolver | Staged spot tasks that span deploys with no resolver set | Set `respawn_credentials:`; the guide's "Surviving a deploy" shows one |
| 29 | T | A rollback to a build from before #74 reads records with `s3:` in `opts`. #75 to #80 crash that task's respawn and delete its pod; a build before #75 respawns it with no staging | Rollbacks while staged `persist: true` tasks run | `stop_tracked/1` those tasks first |
| 30 | P | A `persist: true` task with a non-empty `env:` that is preempted after a restart, and has no resolver, ends with `{:respawn_failed, ...}`: the record holds no env values. A host store that drops `opts[:env]` loses the refusal, and the respawn runs with no environment and calls no resolver. #87 added the resolver | Spot tasks with `on_failure: {:respawn, n}` that span deploys | Set `respawn_credentials:`; keep `opts` whole in a host store |
| 31 | T | A record written before #79 holds plain `env:` values until its next rewrite or its task's end, and DETS may keep freed bytes after that | Hosts upgrading while `persist: true` tasks with secret `env:` run | `stop_tracked/1` those tasks before the upgrade, or delete the DETS file once no task is tracked |
| 32 | T | `Spec.Compute.raw` holds RunPod's echo of the pod `env` in plain. `format_status/1` redacts it in the State line, and `inspect/1` hides it, but a crash report's last message or `inspect(.., structs: false)` prints it (predates #79) | Crash reports of a tracker mid-poll | Drop `env` from `raw` in `Translate`, or redact `:message` in `format_status/1` |
| 33 | T | The owner's `lambda_live` run after #89 confirmed the instance type names, cloud-init starting Docker on the default image, and the `invalid-parameters` echo. Two points still rest on docs: whether the host has `systemd-run`, `mktemp`, bash and a `curl` of 7.55 or later (`-H @-`) for the finish report, since a missing `systemd-run` or a failed `mktemp` stops the script before `docker run`; and whether `docker wait` returns at once for a container left in `Created` by a failed start (#85) | `mix test --only lambda_live` with `LAMBDA_LIVE_CALLBACK_URL` | The owner runs it; a failure there becomes a ticket |
| 34 | O | Two Lambda paths still end only at `max_runtime_ms`, the idle TTL or by hand: a finish report that never lands (callback host down through curl's 5 retries), and a host with no `systemd-run` (the script stops before `docker run`). A failed `docker run` reports 125 since #85. An interactive session with a self-terminating `command:` ends on its report since #96 | Lambda tasks that end `:timed_out`; interactive sessions that end `:idle_timeout` or `:max_runtime` | `run_task/1` always sets `max_runtime_ms`; interactive sessions end at `idle_ttl_ms` unless the app calls `touch/1`, so set `max_runtime_ms` there too |
| 35 | T | The `user_data` script holds every `env:`, `s3:` and `auth:` value in plain on the instance: cloud-init keeps a copy that root reads. Lambda's API never returns it (`writeOnly`) | Instances shared with people who should not hold the credentials | Treat anyone with the instance's SSH key as holding them; prefer short-lived and presigned credentials |
| 36 | T | Lambda's `unhealthy` reads `:running`, so an instance that stays unhealthy keeps billing while a tracker counts it alive | Trackers whose instance never answers | `max_runtime_ms` and `ready_timeout_ms` bound it |
| 37 | T | Instance tags are editable by anyone on the Lambda account. A changed `atlas-created-at` moves `created_at` within the window below | Tag edits on the account | Treat the account as trusted. Since #85 a tag more than ten minutes ahead of the clock reads as no `created_at`, which gets no grace, so it cannot keep an orphan young for ever. Clamping to now would: every list would read a new instance |
| 38 | O | Lambda applies no firewall rules in `us-south-1`, so a spawn there creates no ruleset and its `ports:` URLs do not answer | Callers who spawn in `us-south-1` | Pick another region; #86 opens `ports:` in every other region |
| 39 | T | After the last Req step reveals `user_data`, Finch holds the body: `[:finch, :request, :start]` telemetry metadata carries every value, as it carries the API key header | Hosts that log Finch telemetry | Never log Finch request metadata |
| 40 | T | The values are exported for `docker run`, so `HOME` and `PATH` from `env:` also reach the host's docker client, which reads its config and credential helpers through them. `DOCKER_*` and `LD_*` are refused | Callers who take env names from untrusted input | Take env names only from your own code. Since #85 the exports stay in the subshell that runs docker, so they never reach `systemd-run` or the finish unit |
| 41 | O | A host `TrackingStore` that drops `opts[:respawn_credentials]`, or turns its atoms into strings, adopts the task without its resolver. The respawn then falls back to the app config's, or fails as risk 28 says. A tuple that no longer validates logs a warning at adoption | Adoption warnings naming `respawn_credentials` | Keep `opts` whole; set the app config fallback |
| 42 | T | The resolver tuple's args are stored as given, on disk with the DETS store. A closure or an `ExAtlas.Secret` in them is refused, but a plain-string token lands in the record | Hosts that pass a token in the args | Pass an id in the args and fetch the secret inside the resolver |
| 43 | T | A respawn waits on the resolver inside the tracker, up to `respawn_credentials_timeout_ms` (default 30 s). An `info/1` call on that tracker meanwhile times out at 5 s, as during the provider call that follows | Slow resolvers | Keep the resolver fast; lower the bound |
| 44 | T | Unverified: whether a per-instance ruleset adds to Lambda's default rules or replaces them. If it replaces them, SSH on port 22 closes on every instance with `ports:` | The first `mix test --only lambda_live` run after #86 (it connects to port 22) | The owner runs it; on a failure, the ruleset adds a port 22 rule |
| 45 | O | A terminated instance's ruleset stays until the next spawn with `ports:` sweeps it, since Lambda refuses to delete a ruleset its instance still uses. Each sweep deletes at most 10 and takes about a second a delete | `atlas-` rulesets with no instance in the Lambda dashboard; a spawn that takes long | Spawn again, or delete them by hand |
| 46 | T | The sweep deletes any ruleset named `atlas-<anything>-<8 hex>` with no instance that is 5 minutes old or more, on the whole account: one of a second ExAtlas deployment whose launch has not started, or one you named that way. A node clock more than 5 minutes ahead of Lambda's shortens the 5-minute wait | Rulesets that vanish | Never end your own ruleset names in 8 hex characters after `atlas-`; give each deployment its own account |
| 47 | T | A launch that times out or answers 5xx may have rented the instance. The spawn keeps the ruleset then, so a rented instance has its ports open, and the sweep deletes the ruleset once the instance is gone. A launch that never rented leaves an empty ruleset for the sweep. A rented instance bills until someone terminates it (as risk 34 says) | Launch errors with status 5xx or `:transport` | `list_compute/1`, then terminate by hand |
| 48 | T | With a callback, the Lambda host holds the callback URL and token in a root-only `mktemp` file under `/tmp` from the script's start until the unit starts and deletes it. The container's env holds the same token for the whole task | Instances shared with people who should not post to the callback | The token covers one task and expires with `max_runtime_ms` plus slack; treat SSH access as holding it (risk 35) |
| 49 | T | Narrowed by #110. A token with no attempt (0.8.0's) is refused once a respawn gave the task a pod that signs its attempt. A task that 0.8.0 itself respawned before the upgrade has two claim-less pods, and nothing tells them apart, so the replaced pod's late `finish` still ends the replacement until the task ends (#100) | Tasks 0.8.0 respawned and the upgrade adopted | Nothing to do: the gap closes when those tasks end. Reading a claim-less token as attempt 0 would refuse the current pod's real reports instead |
| 50 | T | Closed by #107. The Limiter bucket is keyed by task and attempt, so a replaced pod's refused reports spend its own budget. Buckets per task now grow with respawns, at most `max_attempts + 1` per kind, and the idle sweep still bounds them | Nothing to watch | Nothing to do |
| 51 | T | Narrowed by #114. A node that dies between renting a replacement and moving the record leaves the replacement orphaned. The respawn now writes `respawning: n` into the record before it rents, so the next boot counts attempt `n` as spent, refuses the orphan's token (410), and gives its own replacement `n + 1`. The orphan still bills until the Reaper deletes it, and a host store that drops `:respawning` adopts as before #114. Since #118 a spawn that can respawn on a provider outside `reap_providers` warns, and a record's pod that reads alive again reports | Warnings from `ComputeServer` that name a pod "that no record names", and from `ExAtlas.Orchestrator` that a provider "is not in :reap_providers"; Vast spot tasks, since `:vast` stays out of the default `reap_providers` (its labels are free text) | Put the provider in `reap_providers`, or delete the named pod by hand. | 52 | T | Vast's API reference and `vast-cli` disagree on four formats: `env` (a Docker-flag string or a JSON object), GPU names (`RTX_4090` or `RTX 4090`), an instance's `ports` (a list of numbers or Docker's map) and `extra_env`. ExAtlas follows vast-cli. A public offer search on 2026-10-02 matched 0 offers for `RTX_4090` and 64 for `RTX 4090`; the rest rests on vast-cli's source | `mix test --only vast_live` | The owner runs it; a failure there becomes a ticket |
| 53 | O | A Vast host can go `offline` mid-session. ExAtlas reads `offline` and `unknown` as `:failed`, which ends the session; it does not move the work to another host | Vast sessions that end `:failed` | Spawn again; a later slice can respawn |
| 54 | T | A Vast rent that times out or answers 5xx may have rented. The spawn returns the error and tries nothing else, and nothing tracks the instance. With `reap_providers: [:vast]` the Reaper destroys it once it is older than `:reap_grace_ms` (#105); without it, it bills until someone destroys it | Rent errors with status 5xx or `:transport` | Add `:vast` to `reap_providers`, or `list_compute(name: ...)` and terminate by hand |
| 55 | T | Vast keeps every `env:`, `s3:` and `auth:` value in plain: `GET /instances` returns them in `extra_env` to anyone with the account's API key, and the host's owner, a marketplace seller, can read the container's environment. ExAtlas keeps them out of `raw` | Credentials passed to Vast spawns | Treat Vast hosts as untrusted with credentials; prefer short-lived and presigned ones (risk 17) |
| 56 | T | Vast's self-deletion rests on three facts only the live API shows: Vast puts `CONTAINER_ID` and `CONTAINER_API_KEY` into a `runtype: "args"` container, that key may DELETE its own instance, and a fresh rent lists a `start_date`. | 57 | O | A SIGTERM to a wrapped container's shell alone (`docker stop`, or a host that stops the instance) waits for the command; the SIGKILL that follows runs no trap, so nothing reports or deletes. Measured with curlimages/curl on PR #108 (stop: 5 s, exit 137, no DELETE) | Tasks that end `:completed` with the instance still listed | Terminate it by hand; `:max_runtime_ms` bounds a task that never ends |
| 58 | T | Vast's spot behaviour rests on facts only the live API shows: an outbid instance reads `actual_status: "exited"` (Vast's docs; ExAtlas reads `exited` as `:stopped`, then `:preempted`); an outbid instance may restart when the price falls, running two copies until the tracker destroys the old one; a bid instance's `dph_total` may differ from its offer's (bid plus storage), which moves `cost_per_hour` and the cost cap after the first poll (#112) | `mix test --only vast_live`, the spot test, which prints `actual_status`, `is_bid`, `min_bid` and `dph_total` | The owner runs it; a failure there becomes a ticket |
| 59 | P | A Vast spot bid at exactly `min_bid` loses to any higher bid, and ExAtlas sends no other price. | 60 | T | A Vast spot task with no `callback:` that finishes deletes its own instance, which reads `:preempted`, so `on_failure: {:respawn, n}` re-runs finished work until the respawns run out | Spot tasks with `command:`, `respawn` and no `callback:` | Pass a `callback:`; the finish report ends the task `:completed` |
| 61 | T | Vast's bill rests on facts only the live API shows: whether a charges row counts only the days asked for, how soon a new hour shows, and that `amount` rounds to 3 decimals. | 62 | O | A stopped Vast instance still bills its disk, and `start/2` fails when the host rented the GPU to someone else.
